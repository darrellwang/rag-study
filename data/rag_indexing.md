# RAG 索引层：切分、元数据与增量更新

## 文本切分策略

切分（chunking）决定了检索的最小单位，是 RAG 里性价比最高的调优点。
chunk 太小会丢失上下文，导致检索到的片段读起来不完整；
chunk 太大则会在一个片段里混入多个主题，稀释向量表示，拉低区分度。

中文语义密度高于英文，chunk_size 常见区间是 300 到 800 字符。
重叠（overlap）通常设为 chunk_size 的 10% 到 20%，用来避免答案正好被切分边界劈开。

三种常用策略：

递归字符切分按「段落 → 换行 → 句末标点 → 字符」逐级降级，
优先在语义边界处断开，适合无结构的纯文本。中文需要把「。！？；」加入分隔符列表。

按 token 切分使用 tokenizer 计数，当下游模型上下文预算很紧、需要精确控制时使用。
注意中英混排时字符数和 token 数差异很大，一个汉字通常占 1 到 2 个 token。

结构感知切分先按 Markdown 标题层级拆成语义块，再对超长块做二次递归切分。
技术文档和 Wiki 首选这种方式。一个重要技巧是把「H1 > H2 > H3」的标题路径
拼进 chunk 正文开头，这样即使命中的是孤立段落，模型也知道它属于哪一节，
对长文档问答的准确率提升非常明显。

## 元数据设计

每个 chunk 至少应该携带来源文件路径、文件名、文件类型。
PDF 还要保留页码，否则用户拿到答案无法回原文核对。
Markdown 应保留标题路径。

元数据的另一个用途是过滤检索（metadata filtering）：
先按部门、时间范围、文档类型把候选集缩小，再在子集内做语义检索。
这在多租户或权限隔离场景下是硬需求——它是安全边界，不是优化手段。

注意 Chroma 的 metadata 只接受标量类型（字符串、数字、布尔），
写入 list 或 dict 会直接报错，入库前必须过滤。

## 幂等入库与增量更新

同一份文件重复上传，如果无条件写入，库里就会出现多份完全相同的 chunk。
检索时 top-k 被同一段内容占满，等于白白浪费上下文预算。

解决方式是内容寻址：chunk 的 id 取 sha1(知识库 id + 来源 + 正文) 的哈希，
写入前先查该 id 是否已存在，已存在则跳过。这样重复上传天然是安全操作。

文档更新则通过「按来源删除 + 重新写入」实现：
metadata 里记录 source，删除时按 source 过滤出全部 chunk 的 id 再批量删除。
没有这个能力，文档改一个字就只能重建整库。

## 常见踩坑

Chroma 会在持久化目录里创建以 UUID 命名的段目录（segment directory）。
如果按「子目录 = 知识库」的约定来列举知识库，这些内部目录会被误认成知识库。
正确做法是只把包含 chroma.sqlite3 的子目录当作知识库。

LMStudio 的 embedding 接口只接受字符串，不接受 token id 数组。
使用 langchain-openai 的 OpenAIEmbeddings 时必须设置 check_embedding_ctx_length=False，
否则会因为默认的 token 长度检查而返回 400 错误。

WSL 环境下如果配置了 ALL_PROXY 之类的代理环境变量，httpx 会尝试
经代理访问 localhost 上的 LMStudio 并失败。
构造 httpx 客户端时传 trust_env=False 可以忽略代理环境变量，直连本地服务。
